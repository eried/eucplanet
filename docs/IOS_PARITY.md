# iOS parity

What the iPhone app does compared with the Android phone app, screen by
screen and feature by feature. Update the row in the same commit that changes
it. How code reaches iOS is in `docs/IOS_SYNC.md`.

Status values:

- **shared**: the code is in `:shared` and runs on both apps unchanged.
- **iOS actual done**: shared, plus the iOS side of its platform seam is written and tested.
- **Android-only**: deliberately not on iOS (for now). Hidden on iOS.
- **not yet**: still in `:app`, so iOS doesn't have it.

| Wheel protocols (Begode, Veteran, Kingsong, InMotion V1/V2, Ninebot) | shared | Adapters, parsers, commands, write queue. Simulator: Begode, InMotion V1 and V2, KingSong virtual wheels decode on iOS. |
| Virtual wheels | shared | |
| Units | shared | `speedUnit(context)` stays in `:app` for Android-only callers. |
| Actions (`ActionCatalog`, `ActionExecutor`) | shared | The list and the executor every surface fires through (dashboard tiles, Flic, volume keys, watch, HUD, voice), with the Legal Mode lockdown gate and custom BLE frames. On iOS the dashboard tiles run through it; music actions do nothing (iOS gives no media keys for other apps), and recording and spoken-command actions wait for those features. |
| Wheel state (`WheelRepository`) | shared | Telemetry, history buffers, charging, lock, light, horn, speed limits, per-wheel profiles. What it takes from the rest of the app comes through `WheelRepositoryPorts.kt`; on iOS (`app/IosWheelPorts.kt`) trips, TPMS caps, external GPS, phone IMU, lockdown and the phone horn answer as switched off until each lands, and wheel profiles are stored in the shared database. Checked on the simulator with a virtual Begode. |
| BLE link | iOS actual done | `WheelLink`: CoreBluetooth scan, connect, service re-routing, notify, paced writes. Auto-reconnect follows Android's rules, now shared (`ble/WheelReconnect.kt`, which Android's BleConnectionManager reads too, and `WheelReconnectHunt`, which the iPhone runs; `WheelReconnectHuntTest`): a wheel that drops with an error is hunted 2 s later by a scan in 60 s windows with 5, 15, 30 and 60 s pauses, shown as searching during a window and Disconnected between; Bluetooth coming back (after 1.5 s) and the app coming to the front restart it; a disconnect the rider asks for, a virtual wheel and the open scan screen do not reconnect, and the scan screen drops only a wheel the app connected by itself. A connect with Bluetooth off waits for it to come on, as on Android. iOS also leaves a CoreBluetooth connect waiting during each window, since a scan with no service filter finds nothing in the background; CoreBluetooth has no low-power scan, so after 10 minutes the hunt keeps its scan. RSSI is read once a second while connected, for the BT signal metric. Android's status-133 retries have no iOS counterpart. The simulator has no Bluetooth and a virtual wheel never drops (it is not hunted on either phone), so the hunt is checked by the tests only; not yet tested on a real wheel. |
| Settings storage | iOS actual done | Same JSON blob in DataStore (`SettingsStore`, `SettingsRepository`, `SettingsJson`). First-run units on iOS follow the phone's region alone; Android also checks the cell network. |
| Trip database | iOS actual done | `AppDatabase` and its DAOs are shared Room (KMP). Android builds it as before (framework SQLite, `eucplanet.db`, the migrations in `AppModule`); iOS opens the same schema on the bundled SQLite in Documents. An iOS install starts at the current version, so a future schema bump needs a common-code migration for iOS. `AppDatabaseIosTest` checks it on the simulator. |
| Themes | shared (partial) | `ThemeController` and the first-run migration are shared; iOS resolves the same `activeThemeName` from settings.json, so a built-in theme picked on Android shows on the iPhone after a Dropbox sync (on the next launch, as on Android). Saved custom themes live in Documents/themes on iOS and sync both ways with Dropbox's /themes in Sync now, through the same `syncJsonFolder` Android uses; the theme picker and the editor widget are not on iOS yet. The iOS status bar does not follow a light theme yet. |
| Strings (23 locales) | iOS actual done | Compose resources generated from `app/src/main/res` (docs/IOS_SYNC.md). Latin American Spanish still reads Spain's Spanish on iOS: the es-419 lookup is not wired yet. In-app language picker not on iOS; it follows the iPhone's language. |
| Voice alerts (TTS) | shared (partial) | What each report says (`VoiceReports`, `VoiceReportPlan`, the pills) is shared. iOS speaks it through AVSpeechSynthesizer (`app/IosVoice.kt`): the periodic report on the same interval and "announce when" rules as Android, the dashboard's voice button, the welcome, event lines and alarm voice text, at the voice settings' rate, volume and language. On iOS the report words follow the phone's language rather than the voice's, and there is no voice picker, audio focus choice or output channel. Spoken commands are not on iOS. Not yet heard on a phone. |
| Alarms | shared (partial) | The editor (`AlarmSettingsContent`, `AlarmViewModel`) is shared; on iOS it shows in Settings, as on Android. Rules live in the shared database and sync with settings.json (earlier builds' alarm_rules.json is moved in once). The engine (`AlarmEngine`, the evaluator, the wheel pass) is shared too and fires on iOS through `IosAlarmOutputs`: the voice speaks and the phone buzzes. Beeps and the Beep Studio's live tone render with the shared `ToneSynth` (the same samples as Android) and play through AVAudioEngine (`IosTonePlayer`, ducking other audio). GPS alarms need phone location; no watch or car display. Not yet heard on a phone or tried on a ride. |
| Trip recording, GPS | iOS actual done (partial) | The CSV is the shared `CsvWriter` (`CsvWriterTest` runs on both), so an iPhone trip is the same file an Android one is, in Documents/trips with the same trip row in the shared database. `app/IosTrips.kt` records at the rider's interval with the same row rules (fresh, accurate fixes only; the wheel's per-segment distance, else the GPS's) and auto-records on motion through the shared `AutoRecordPolicy`. GPS comes from CoreLocation through `iosApp/LocationBridge.swift` (a Kotlin delegate was never called back), and keeps running in the background while recording. GPS distance is haversine, where Android's `Location.distanceTo` is ellipsoidal (well under 1% apart). A finished trip queues the Dropbox pass when Dropbox is linked. A recording the app was killed in is finalized from its CSV at the next start, or dropped with its file when nothing was written, the same sweep Android runs (`recoverKilledRecordings`, `KilledRecordingSweepTest`). The discard grace before a sync exists on Android only with a backup folder, so on iOS, as on an Android phone without one, a stopped trip is final at once. Not yet: GPS power tiers, wheel identity in the Extra column, the external GPS box. Checked on the simulator with a simulated route; not yet on a ride. |
| Background connection | not yet | `bluetooth-central` background mode is in Info.plist. |
| Motor sound | not yet | AVAudioEngine. |
| Notifications | iOS actual done (partial) | The charge alerts post through UNUserNotificationCenter (`app/IosChargeAlerts.kt`) and show over the open app too; a tap opens the charging monitor. Other notifications are not on iOS yet. |
| Backups (Dropbox), share, import | iOS actual done (partial) | Trips, settings.json (settings and alarm rules) and saved themes both ways with Dropbox, through the same shared passes Android runs (`data/sync/DropboxTripSync.kt`): the same /trips folder and file names, the same rules (size and content hash against the last-synced fingerprint, one question for every real conflict, the background pass never overwriting another phone's edit, a pull only when asked, archives followed from another phone), and the same pending count and progress bar in Settings -> Backups. Sync now is Android's Sync all. The quiet pass (Android's DropboxSyncWorker) runs in the app: 10 s after launch, on every return to the front, when a trip finishes, every pendingUploadIntervalMin while open, and on Android's retry curve (15 s doubling to 5 min, 30 min after a refusal). Linking asks for the library, as on Android. Android's worker waits for any connection (no Wi-Fi only setting exists); iOS just tries, and a pass with no network fails and backs off on the same curve. Not yet on iOS: sync while the app is closed (needs BGTaskScheduler), the overlays folder, the backup folder. Tested against an in-memory Dropbox (`FakeDropbox`, on the JVM and the iOS simulator); linking and syncing not yet tried with a real account on iOS. |
| eucstats leaderboards | iOS actual done (partial) | The client, repository, request hash, meta envelope and the upload sweep are shared (`data/eucstats/`, `data/sync/EucStatsSweep.kt`), and so are the join, profile and card screens (`ui/settings/eucstats/`). iOS (`app/IosEucStats.kt`) registers and uploads as `platform: "apple"`, keeps the rider id in Documents/eucstats_riderid.txt (Android keeps it in the backup folder, so a reinstall without an iCloud backup loses it), picks the picture through the photo library's own square crop, and sweeps when a trip finishes, at launch and when the app comes to the front, retrying on Android's backoff while it stays open. Not yet: background uploads, and App Attest: iOS sends `{"type":"app_attest","token":""}`, which the server takes only in stub mode, so real App Attest needs the server to verify it first. `EUCSTATS_API_BASE_URL` in the launch environment (or the Info.plist key `EucStatsApiBaseUrl`) points a dev build at a local server. Checked on the simulator against a local eucstats: join with a photo, card, profile, trips uploaded and validated. |

## Parity pass (2026-11-08)

Both phones driven by a virtual Begode Master, both on imperial units and
the light theme, screenshots side by side: Android on the `euc35` emulator
(adb), iOS on the iPhone 17 simulator (the `EUC_SCREEN` launch routes, plus an
XCUITest runner outside the repo for taps and scrolls while the Mac was
locked). Date format and the decimal comma differ by locale, as expected.

Fixed since: the dashboard footer shows the app's version on any Xcode
build (`iosApp/stamp-version.sh` stamps Android's versionName and the commit
count, as testflight.sh does); the "Needs attention" icon and list
(`app/IosAppHealth.kt`) raise the iPhone's own warnings (location refused,

battery optimisation, picture-in-picture and the like; a recording killed
mid-way no longer leaves a 0 s trip; the layout editor no longer offers Listen
