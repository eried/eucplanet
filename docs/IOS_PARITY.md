# iOS parity

What the iPhone app does compared with the Android phone app, screen by
screen and feature by feature. Update the row in the same commit that changes
it. How code reaches iOS is in `docs/IOS_SYNC.md`.

Status values:

- **shared**: the code is in `:shared` and runs on both apps unchanged.
- **iOS actual done**: shared, plus the iOS side of its platform seam is written and tested.
- **Android-only**: deliberately not on iOS (for now). Hidden on iOS.
- **not yet**: still in `:app`, so iOS doesn't have it.

## Back and closing

The iPhone has no system back, so every window has a way out the rider can
see: a Cancel or Close in its button row, or, for a window without one (the
crew pass card), the shared X `ui/common/CloseIconButton.kt` at the end of its
header. Android uses the same X, there is no per-platform gate. Bottom sheets
keep their drag handle (swipe down or tap the scrim), the iOS sheet idiom.

A swipe in from the left edge is back. Compose Multiplatform 1.11 turns it
into a back event on its own (the start edge is always back; nothing to set in
`ComposeUIViewController`) and gives it to the newest enabled handler, the
common `BackHandler` from `ui-backhandler`, wrapped once as
`app/IosBack.kt` (`IosBackHandler`). MainViewController registers one on every
screen but the dashboard, with the same target as the screen's back arrow
(scan, settings, Flic, trips, trip detail, the EUC viewer, trip meter, metric
detail, the charging monitor, and the scan screen under Legal Mode); the crew
pass registers last, so the swipe closes it before the screen under it. The
hosts that had a no-op `BackHandler` now pass it through: a trip import
swallows the swipe (`IosRecordingHost`), and so does the locked screen
(`IosLockdown.Host`), as Android's back is swallowed there.

Dialogs, sheets and popups: Compose's own dialog handler takes only an
instant back, so on its own it swallowed the swipe and the dialog stayed
open. `IosBackSwipeBridge` (mounted once at the root) sits in front of every
handler at overlay priority, takes the swipe and, when it completes, replays
it as an instant back to the next handler in line: the open dialog's dismiss,
else the screen's `IosBackHandler`. A swipe let go of early is cancelled. The
bridge is always on, so the left edge also listens on the dashboard, where a
swipe does nothing. Android is untouched: all of this is in iosMain.

Checked on the simulator (iPhone 17, iOS 26.5, virtual Master): the swipe goes
back from Settings, the trip list, trip details and the battery monitor; it
closes Needs attention over the dashboard and the Delete trip question over
the trip list without leaving the list or deleting; it closes the crew pass
over Settings. The pass's X closes it from the scanner and from Enter
manually.

## Real-wheel BLE review (2026-11-10)

A code review of `IosWheelLink` against Android's `BleConnectionManager`
before the first ride with a real wheel (the simulator has no Bluetooth).
Family picking, the re-route by discovered services, each family's
characteristics and write type, init, polling and keep-alives, the InMotion
V1 password and the Ninebot key exchange are shared code and match.

Fixed:

- Frames were not split: an InMotion V1 frame (22 bytes or more) went out as
  one GATT long write, the cause of V1 link drops Android fixed with
  `writePieces`. iOS now writes the 20-byte pieces, each acked.
- A write-with-response was resent on a slow ack, up to 8 times; Android
  never resends a write the stack accepted. iOS sends once and logs a late
  ack or a refusal, as Android does.
- The write queue was filled from the polling thread and drained on the main
  thread with no lock; writes now enter it on the main thread.
- A missing characteristic left the link initializing forever; it now gives
  up with Android's "Adapter characteristics not found" line.
- No-response writes wait (up to 200 ms) for CoreBluetooth to have room,
  instead of being dropped when its buffer is full.
- The log carries the write characteristic's properties and write type
  (`BleProfile.writeTypeNote`, both phones) and the subscribe result.

Left, needs a wheel to judge: iOS negotiates the MTU itself, where Android
skips it for KingSong and InMotion V1 modules that hang the exchange; no
second CCCD write on HM-10 wheels (Begode, KingSong); no 35 s connect
watchdog and no 15 s no-data release; polling wheels (InMotion, Ninebot Z)
may stop being asked while the app is suspended in the background; the
family is picked from the cached GAP name, not the advertised name.
