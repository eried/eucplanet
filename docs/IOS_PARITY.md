# iOS parity

What the iPhone app does compared with the Android phone app, screen by
screen and feature by feature. Update the row in the same commit that changes
it. How code reaches iOS is in `docs/IOS_SYNC.md`.

Status values:

- **shared**: the code is in `:shared` and runs on both apps unchanged.
- **iOS actual done**: shared, plus the iOS side of its platform seam is written and tested.
- **Android-only**: deliberately not on iOS (for now). Hidden on iOS.
- **not yet**: still in `:app`, so iOS doesn't have it.

The welcome tour runs without its clips. The settings button opens the shared Settings screen. | Voice alerts (TTS) | shared (partial) | What each report says (`VoiceReports`, `VoiceReportPlan`, the pills) is shared. iOS speaks it through AVSpeechSynthesizer (`app/IosVoice.kt`): the periodic report on the same interval and "announce when" rules as Android, the dashboard's voice button, the welcome, event lines and alarm voice text, at the voice settings' rate, volume and language. | Trip recording, GPS | iOS actual done (partial) | The CSV is the shared `CsvWriter` (`CsvWriterTest` runs on both), so an iPhone trip is the same file an Android one is, in Documents/trips with the same trip row in the shared database. `app/IosTrips.kt` records at the rider's interval with the same row rules (fresh, accurate fixes only; the wheel's per-segment distance, else the GPS's) and auto-records on motion through the shared `AutoRecordPolicy`. GPS comes from CoreLocation through `iosApp/LocationBridge.swift` (a Kotlin delegate was never called back), and keeps running in the background while recording. GPS distance is haversine, where Android's `Location.distanceTo` is ellipsoidal (well under 1% apart). A finished trip queues the Dropbox pass when Dropbox is linked. A recording the app was killed in is finalized from its CSV at the next start, or dropped with its file when nothing was written, the same sweep Android runs (`recoverKilledRecordings`, `KilledRecordingSweepTest`). ## Real-wheel BLE review (2026-11-10)

A code review of `IosWheelLink` against Android's `BleConnectionManager`
before the first ride with a real wheel (the simulator has no Bluetooth).
Family picking, the re-route by discovered services, each family's
characteristics and write type, init, polling and keep-alives, the InMotion
V1 password and the Ninebot key exchange are shared code and match.

Fixed:

- Frames were not split: an InMotion V1 frame (22 bytes or more) went out as
  one GATT long write, the cause of V1 link drops Android fixed with
  `writePieces`. iOS now writes the 20-byte pieces, each acked.
- A write-with-response was resent on a slow ack, up to 8 times; Android
  never resends a write the stack accepted. iOS sends once and logs a late
  ack or a refusal, as Android does.
- The write queue was filled from the polling thread and drained on the main
  thread with no lock; writes now enter it on the main thread.
- A missing characteristic left the link initializing forever; it now gives
  up with Android's "Adapter characteristics not found" line.
- No-response writes wait (up to 200 ms) for CoreBluetooth to have room,
  instead of being dropped when its buffer is full.
- The log carries the write characteristic's properties and write type
  (`BleProfile.writeTypeNote`, both phones) and the subscribe result.

Left, needs a wheel to judge: iOS negotiates the MTU itself, where Android
skips it for KingSong and InMotion V1 modules that hang the exchange; no
second CCCD write on HM-10 wheels (Begode, KingSong); no 35 s connect
watchdog and no 15 s no-data release; polling wheels (InMotion, Ninebot Z)
may stop being asked while the app is suspended in the background; the
family is picked from the cached GAP name, not the advertised name.
